### 0. A hazard that must be fixed in PU-1: the workflow record is inside the publish root

This repository is the GitHub Pages user site *and* the AI-DLC workspace. The
`aidlc/` tree is version-controlled by design (project `CLAUDE.md` § Git
Integration) and sits at the repository root, which is also the site's publish
root. Unless the chosen generator is explicitly told to exclude it, the entire
decision record — intent statement, scope document, interview answers, this file
— is published to the public web under `rue-asha.github.io/aidlc/…`.

This is not hypothetical for the most likely stack: Jekyll on GitHub Pages
processes every path that does not begin with `_` or `.`. `aidlc/` begins with
neither. Markdown files there with front matter are rendered as pages; those
without are copied verbatim. Either way they are publicly fetchable. `.claude/`
is dot-prefixed and would be excluded by Jekyll's defaults, but that protection
disappears the moment the stack changes or a raw copy step is introduced.

**Proposed practice, stack-neutral:** the published output contains the site and
nothing else. Whatever generator is chosen must exclude `aidlc/` and `.claude/`
from its output (`exclude:` in `_config.yml` for Jekyll; `ignoreFiles` or module
mounts for Hugo; an explicit copy list for a hand-rolled build).

**Proposed acceptance criterion for PU-1**, testable and pass/fail: after the
first deploy, `GET /aidlc/` and `GET /aidlc/spaces/default/memory/project.md`
against the live URL both return 404. If either returns 200, the skeleton is not
done. This belongs in PU-1 because PU-1 is the Bolt that proves the publishing
path, and this is a property of the publishing path.

### 1. Naming, layer boundaries, and file organisation

**The boundary that matters is not two-way but three-way.** The draft speaks of
"content" and "site code". A static content site actually has four layers, and
the tangle the question is about happens at the seam between the second and
third:

| Layer | What it holds | May depend on |
|---|---|---|
| Content | Post and project files: front matter plus prose | Nothing |
| Templates | Page layouts, partials, reusable includes | Content *fields*, by name |
| Styles | The visual treatment (PU-5 lands here) | Templates, by class/selector |
| Build config | Generator config, deploy workflow, formatter/linter config | Everything |

**The one rule that keeps them from tangling as posts accumulate:** a content
file contains no template logic, and a template contains no content. Stated so
it can be checked: a post file is front matter plus prose, and nothing in it
would break if the site were regenerated by a different tool.

The way this rule actually gets broken is specific and worth naming now, because
it is invisible until it is expensive: a post needs something the layout does
not do — a side-by-side image pair, a callout, a diagram wrapper — and the
author pastes raw markup with inline styles into the post. It works. It happens
again in post four, copied and slightly changed. By post ten the presentation of
the site lives in ten prose files and cannot be changed in one place. **Proposed
practice: when a post needs a presentation capability the layout does not have,
it becomes a named reusable include used by name from the post, never one-off
inline markup.** The first time costs ten minutes more; every later time costs
less.

**Proposed layout**, expressed as a shape rather than a stack:

```
<site-root>/
  content/
    writing/<slug>/index.md       # the post, plus its own images alongside
    projects/<slug>/index.md      # the write-up, plus its own images
    about.md
  layouts/                        # or _layouts/, _includes/ — stack's idiom
  styles/
  <generator config>
  404.html                        # required; see §2
```

- **One directory per post, with its images inside it.** Deleting a post deletes
  its images and orphans nothing; moving a post moves its images with it. The
  alternative — one global images folder — accumulates files nobody can prove are
  still referenced, and on a site with no analytics nobody ever will. If the
  chosen generator does not support page bundles, fall back to
  `assets/writing/<slug>/`, which preserves the same one-directory-per-post
  discipline without the generator's help.
- **The file name is the URL.** Lowercase, kebab-case, ASCII only. No spaces, no
  capitals, no characters that need percent-encoding.
- **Date lives in front matter, not in the sort.** Whatever orders the Writing
  list must read the declared date, never the file's modification time — git does
  not preserve mtimes, so a fresh clone or a CI checkout gives every file the same
  timestamp and the list silently reorders. This is a cheap mistake to make and an
  invisible one to have made.
- **Whether the date also prefixes the filename** (`2026-03-12-my-post.md`) is a
  genuine trade-off, not a default: the prefix keeps the editor's file list in
  chronological order for free, but on some generators it also pushes the date
  into the published URL. Worth one interview question (§5, Q2) rather than a
  guess.

**Naming conventions.** Agree with the draft: language-idiomatic, no
project-wide rename rules. One convention is *not* language-idiomatic and does
need stating, because it is the only naming decision here with an irreversible
cost:

> **Published URL slugs never change.** A renamed slug breaks every search
> result and every link anyone shared, and with analytics excluded from scope the
> author will never learn that it happened.

GitHub Pages has no server-side redirects, so the remedy if a slug must change
is leaving a stub page behind or adding a redirect plugin — a Construction
decision, but one that only exists because the rule was broken. Record the rule
under Code Style now; it costs nothing while there are two posts.

### 2. Error handling at the boundaries that actually exist

This site has no database, no API, no auth. The construction-phase rule "always
include error handling at integration boundaries" still applies — the boundaries
are just different ones. There are four:

**Boundary 1 — content file into the build.** The failure is a post whose front
matter is malformed, missing a required field, or carries an unparseable date.

- **The build must fail. It must not skip the file.** A generator that quietly
  omits an unparseable post is the single worst possible behaviour for this site,
  because Flow 3 promises commit-and-it-appears: the author pushes, sees a green
  build, and the post is simply not there, with nothing anywhere saying why. Skip-
  on-error converts a two-minute typo into a silent content loss the author
  discovers weeks later, or never.
- **This is a stack-selection criterion, not a preference.** Whichever generator
  is chosen must be verifiable as failing loudly on malformed content, and PU-1
  must prove it: commit a post with a deliberately broken front-matter block, and
  confirm the build fails and the previously live site stays up. Rehearse it once,
  like the rollback.
- **The required-field set is derivable from the approved wireframes** and should
  be written down so "malformed" has a definition:

  | File kind | Required | Optional, with a stated behaviour when absent |
  |---|---|---|
  | Post | title, one-line summary, date | — |
  | Project | name, one-line summary, year, type, tools, repo | live URL — the rail row is **omitted**, not rendered empty (`wireframes.md` § Project, [Q6]) |

  Missing required field = build failure naming the file and the field. Missing
  optional field = the documented omit behaviour, silently and by design. The
  distinction is the schema; encoding it is what makes "malformed" checkable
  rather than a judgment call.

**Boundary 2 — build into published output.** The failures are a dead internal
link and a missing asset reference.

- **Internal links are build-blocking; external links are report-only.** A link
  between Home, Writing, Post, Projects, Project and About that does not resolve
  is a defect in this repository and the build should fail on it. A dead
  third-party URL is somebody else's outage, and failing the build on it means the
  site stops publishing because an unrelated website went down. The lead's check
  list (Testing Posture, item 2) says "internal links resolve" and is right; this
  spells out the half it leaves implicit, so Construction does not wire a checker
  that hits the network on every build.
- Missing asset references get the same treatment as internal links: blocking.
  A post referencing an image that is not in the repository is a broken post.

**Boundary 3 — published page into reader.** The only failure that can occur is
a bad URL.

- **`404.html` must exist at the site root, carry the global shell, and link to
  Writing and Projects** (`user-flow.md` Flows 1 and 2 both name it). This reads as
  a design requirement and is really a build requirement: the generator must emit
  it and GitHub Pages must serve it for unmatched paths. PU-1 acceptance: `GET
  /definitely-not-a-page` returns the styled 404, not the platform's default.

**Boundary 4 — push into publish.** The lead owns this one and has it right. One
addition from the code side: the mandated rule "serve pages complete, with no
loading state" is a hard constraint on the stack, and it has a one-line test —
**load any page with JavaScript disabled; if content is missing, the rule is
broken.** A framework that hydrates content client-side by default violates a
Mandated rule regardless of how good it is otherwise. Worth carrying into the
stack decision as a pass/fail filter rather than discovering at Construction.

### 3. "Advisory on content, blocking on code" — the right instinct, the wrong cut

The intent is correct: a style opinion must never stop a post going live. But
the line as written conflates two different things about content, and read
literally it licenses exactly the silent-skip failure the same draft's Testing
Posture section warns about. Content has structure *and* prose, and they need
opposite treatment.

**Proposed replacement for that bullet:**

| What is being checked | Treatment | Why |
|---|---|---|
| Content **structure** — front matter present, required fields, date parses, internal links resolve | **Blocking** | Not style. A post that fails these does not appear, and nothing tells the author. §2 Boundary 1. |
| Content **prose style** — line length, heading case, punctuation, inline HTML, trailing whitespace | **Off, or advisory-only** | An opinion about quote style must never stop a post going live. This is the ceremony the scope forbids. |
| **Site code** — templates, styles, build config | **Blocking** | It can break pages other than the one being edited. |

These are two different tools, and conflating them is how the practice gets
mis-implemented. A Markdown linter (markdownlint or similar) checks prose style
and knows nothing about whether `date:` is present; front-matter validation is
the generator's job or a small schema check. Concretely, if markdownlint is
adopted: disable MD013 (line length) outright for post content, and do not treat
its output as a gate.

**"Blocking" also needs a *where*, and the draft does not say.** With no PR and
no reviewer — the lead's own proposed default — "blocking" can only mean blocking
the local commit or blocking the publish. Recommendation:

- **Formatter: on save, in the editor. Not a commit hook.**
- **Formatter in check mode + linter: in the build, blocking the publish.**

The build check is the backstop that catches a file edited outside the editor or
on another machine; the on-save is the habit that means it never triggers. A
pre-commit hook adds latency to every commit and fails on things unrelated to the
change; a solo author learns `--no-verify` exactly once and then uses it forever,
at which point the hook is worse than nothing because it is believed to be
running. This is the single most reliable erosion pattern in solo repositories.

### 4. Code style with no stack yet — and what actually survives

**Agreed and worth keeping verbatim:** decide the formatter and linter at the
same time as the stack; accept defaults rather than tuning; do not reformat
prose. Three additions.

**(a) Pin *when* the tooling lands: PU-1, not "with the stack".** The draft's
own rationale — that retrofitting produces one enormous reformatting commit that
buries the change that mattered — is a sequencing constraint, not just a
preference. Formatter config, linter config, and the first formatting run belong
in the skeleton Bolt, so PU-2 through PU-6 are written formatted from the first
line. Say PU-1 explicitly; "with the stack" is vague enough to slip.

**(b) Make the prose exemption operational.** "Should not be allowed to reflow
prose" is a requirement; the implementation is a path-scoped exclusion of the
content tree from the formatter. If Prettier is chosen, the exact knob is
`proseWrap: "preserve"` plus a `.prettierignore` entry for `content/`. Naming it
here saves Construction the rediscovery, and the failure mode if it is missed is
memorable: the formatter rewrites the line breaks of every post on its first run
and the diff of the next real change is unreadable.

**(c) What a solo author sticks to versus what erodes.** From the same evidence
the draft has — one person, no reviewer, no deadline:

| Survives | Erodes |
|---|---|
| Zero decision cost at the moment of writing: format on save, one formatter, no config to think about | Anything requiring a remembered command |
| A build that fails loudly and says which file and which field | A report the author has to go and look at |
| One tool with clear jurisdiction over each file type | Two formatters with overlapping claims on the same file, silently fighting |
| Rules the author chose | A long inherited rule list nobody agreed to, which gets bulk-disabled at the first inconvenient failure |
| Checks that only fail on something the author just changed | Checks that fail on unrelated pre-existing issues — these teach the author to ignore the check |

The last row is the one that decides whether the accessibility check in the
lead's Testing Posture survives past month two. If it reports thirty
pre-existing issues on every build, it will be switched off. It needs to start
from a clean baseline in PU-1, while the site is six pages, and stay green.

### 5. The Way of Working split: sound, but drawn on the wrong axis

**The split is not a contradiction of trunk-based development.** Trunk-based
development's actual invariant is that work integrates into trunk continuously
and no branch outlives a day or two. Committing straight to `main` is the
strongest possible form of that, not a violation of it — a branch exists to hold
work that is not yet safe to integrate and to run a check before it lands.
Content is safe to integrate, and under the lead's own proposal the checks run on
`main` anyway. Both paths land on `main`; neither creates a long-lived branch.
Endorsed.

**But the axis is wrong, and the draft has no answer for the case the question
names.** The table splits by *what kind of file you touched*. Git operates on
commits, and the common real change is a post plus the layout tweak it needs.
Under the table as written, that commit is both rows at once and the author has
to invent an answer while wanting to publish.

**Proposed reformulation — split by blast radius, not by file kind:**

> A change that can only break the page it is in goes straight to `main`.
> A change that can break pages other than the one being edited goes through a
> short-lived branch and squash-merges to `main`.

This absorbs the mixed case cleanly and makes the content/code table a
*consequence* rather than a rule: a new post goes straight to `main` because it
can only break itself, not because it is content. Worked through the three real
versions of "a post that needs a layout tweak":

| The tweak | Path | Why |
|---|---|---|
| Cosmetic, scoped to that page — a spacing fix, one new utility class | One commit, straight to `main` | Splitting it across two paths is the ceremony the scope forbids, and the rollback is *better* as one commit: `git revert` takes the post and its tweak together, leaving nothing half-applied. |
| A new reusable capability the post is the first to use — a new include or shortcode | Branch the capability, land it alone, then commit the post | Keeps the capability reusable instead of welded to one post, and keeps the post's own commit about the post. |
| A change to a shared layout that touches every existing page | Branch | A broken shared layout takes the whole site down. This is the one place the check-before-live gate is worth its friction. |

**A coupling the evidence table misses.** `evidence.md` lists "branch or
self-merged PR" and "are content commits exempt from branching" as two
independent unknowns. They are one decision. If the author answers "no PR, checks
run on `main` after the merge", then a branch buys nothing at all except the
chance to run the build locally before merging — and the honest practice becomes
"commit to `main`, run the build locally before pushing", with no branch anywhere.
Asking these separately can produce an incoherent pair: branch for code, no PR,
checks only after merge — friction with no gate on the other end. **Ask them as
one question** (§6, Q4).

**One regime note the practice should carry**, because two different readers will
use it: during AI-DLC Construction, code work runs in worktrees, which are
branches by construction, base `main`, squash to `main` — that is settled and
unaffected. The direct-to-`main` path is what the author uses *afterwards*,
living with the site. The practice should say which regime each row describes, or
it will read as contradicting the worktree flags table three paragraphs above it.

### 6. Gaps the Step 4 interview must resolve

Written to be answerable by a solo developer with no framework vocabulary. Four
options plus Other each, per the project's own question-authoring rule. Each
carries a suggested default so the author can agree quickly.

**Q1 — You push a post and its header block has a typo (a missing title, or a
date the site cannot read). What should happen?**
A. Nothing publishes; the build fails and tells you which file and what is wrong,
and the site as it was stays live. *(suggested)*
B. The site publishes and that one post is quietly left out.
C. The site publishes and the post appears with a placeholder title.
D. Publish it, and email me about it afterwards.
*Why it matters:* with B, you push, the build goes green, and your post simply is
not there — with nothing anywhere saying why. This also decides which tools are
usable, so it is worth settling before the stack.

**Q2 — Should a post's web address include its date?**
A. No — `rue-asha.github.io/writing/my-post/`. *(suggested)*
B. Yes — `rue-asha.github.io/writing/2026/03/my-post/`.
*Why it matters:* whichever you pick, the address cannot change later without
breaking every link anyone shared and every search result — and since there are
no analytics, you would never find out it happened. Dates in the address make
older posts look older; leaving them out keeps the address about the topic.

**Q3 — Where should a post's images live?**
A. In a folder next to the post, one folder per post. *(suggested)*
B. All images together in one folder for the whole site.
*Why it matters:* with A, deleting a post deletes its images and nothing is left
behind; with B, after a year nobody can tell which images are still used.

**Q4 — For a change that affects every page — the header, the navigation, the
site-wide styling — do you want to try it somewhere safe first, or commit it and
fix it if it looks wrong?** *(Writing a post is not this question — that always
goes straight to `main`.)*
A. Commit straight to `main` and fix forward; if it looks wrong, undo the commit.
*(suggested — simplest, and undoing is one command on a static site)*
B. Do it on a side branch, check the build passes, then merge it.
C. Do it on a side branch and open a pull request against yourself, so the checks
run before it goes live.
*Why it matters:* this is one decision, not two. If you pick A, there is no
branch anywhere and the practice is simply "run the build locally before you
push". Answering it settles both open Way of Working questions at once.

**Q5 — Should the tool that tidies your code also touch the text of your posts?**
A. No — leave post text exactly as I wrote it. *(suggested)*
B. Yes, tidy everything the same way.
*Why it matters:* automatic tidying rewrites line breaks. Where you chose to
break a line in a post is usually deliberate, and after this runs once, the next
real edit's diff is unreadable.

**Q6 — When something is wrong, where do you want to find out?**
A. On my machine, before I push — the build runs locally and I look at it.
B. After I push — GitHub emails me if the build failed. *(suggested; it is the
one that works when you are pushing from a phone or another machine)*
C. Both.
*Why it matters:* this is the unresolved "how do I know publishing failed"
question from the flows, and it also decides whether the style checks block your
commit or just the publish. If you pick B, confirm the notification actually
reaches an address you read — a warning nobody receives is not a warning.

**Q7 — What do you promise to write at the top of every post and every project?**
For posts: title, one line saying what it is about, date. For projects: name, one
line, year, type, the tools used, and a repository link — with a live URL only
where there is one. *(This is what the approved wireframes already draw. Confirm
it, or say what you would rather not have to fill in every time.)*
*Why it matters:* whatever is on this list becomes something the build refuses to
publish without. Anything you would resent typing every time should come off the
list now rather than be worked around later.

  accepted rather than tuned — retrofitting a formatter later buries the real
  change under a reformatting commit, and a config nobody tuned is a config
  nobody argues with.
- AGREE: Formatting must be automatic or it does not happen — correct for a solo
  author, and the strongest claim in the Code Style section.
- AGREE: Markdown prose in posts is authoring, not code, and must be exempt from
  reflowing — this is the difference between the formatter being invisible and
  being switched off at post five.
- AGREE: Naming follows the language's own idiom with no project-wide rename
  rules — nothing here justifies a bespoke convention.
- AGREE: Content commits and code commits are different paths to `main`, and this
  is a specialisation of trunk-based development rather than a contradiction of it

- AGREE: `main` is production, there is no staging, and a self-approval gate
  would record nothing — stated plainly rather than adapted quietly, which is the
  right call.
- AGREE: `git revert` plus a push is the whole rollback, and it should be
  rehearsed once rather than assumed — a static site with no state outside the
  repository genuinely has no harder case.
